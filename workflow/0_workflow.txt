DOMAIN WORKFLOW

Purpose
Run the domain research and compilation process from a fixed Domain D to a controlled foreground domain file.

Normative input (read only)
000_DOMAIN.txt
background/000_DOMAIN_research.txt

Input
DOMAIN D = canonical generic Domain mnemonic or canonical Industry Domain mnemonic.
DOMAIN code = NNN.
PROBLEM P = controlled Problem ID when LEVEL=CASE.
For an Industry Domain, code, mnemonic, Industry, Primary Domain, Territory, and Macro Domain anchor are fixed before the workflow starts.

Workflow prompts (read only)
workflow/1_research.txt
workflow/2_background.txt
workflow/3_compile.txt
workflow/4_foreground.txt
workflow/5_output.txt

Output
Background: background/<NNN>_<D>_research.txt
Foreground: <NNN>_<D>.txt

Roles
1. R Researcher: expand.
2. B Background Controller: check research.
3. C Compiler: contract.
4. F Foreground Controller: control content.
5. O Output: normalize representation.

Workflow
Problem layer R → B → C → F → O
→  Case layer R → B → C → F → O


Problem layer

Problem routing
candidate
→ in scope / out
→ owned here / elsewhere / borderline
→ distinct / merge / variant / unresolved
→ integrated / components
→ Regime
→ Structure
→ dependencies
→ numbering
→ Candidates shortlist

1. Research problems (R)
Input: research.txt with LEVEL=PROBLEM and DOMAIN=D.
Research the domain territory, candidate problems, boundaries, aliases, variants, dependencies, Template evidence, and supporting sources.
Output: problem background v#.1.

2. Control problem background (B)
Input: background.txt with LEVEL=PROBLEM and DOMAIN=D.
Check coverage, evidence, boundaries, granularity, ownership, dependencies, and Template support.
Return defects to R until controlled.
Output: controlled problem background v#.2.

3. Compile problem set (C)
Input: compile.txt with LEVEL=PROBLEM and DOMAIN=D.
Compile the controlled background into the foreground content defined by 000_DOMAIN.txt.
Derive sequence and numbering under 000_DOMAIN.txt.
Output: numbered problem set in foreground v#.1.

4. Control problem foreground (F)
Input: foreground.txt with LEVEL=PROBLEM and DOMAIN=D.
Check semantic fidelity, completeness, ontology, ownership, ratings, dependencies, sequence, numbering assignments, and claims against 000_DOMAIN.txt and the controlled background.
Return content-compilation defects to C. Return substantive evidence defects to R/B.
Output: content-controlled numbered problem set in foreground v#.2.

5. Normalize problem output (O)
Input: output.txt with LEVEL=PROBLEM and DOMAIN=D.
Normalize the content-controlled foreground under workflow/5_output.txt.
Do not change claims, IDs, numbering, classifications, dependencies, ratings, Templates, or tags.
Output: presentation-controlled foreground v#.2.

STOP -- Human inspection and explicit go-ahead required before case research.


Case layer

Case work is selective and runs one controlled Problem P at a time.
The first Case for P is always INDUSTRY.
The Case layer may be rerun as CANDIDATE or CLIENT evidence is added or as a Case advances through proprietary analysis.

6. Research cases (R)
Input: research.txt with LEVEL=CASE, DOMAIN=D, and PROBLEM=P.
Use P as the fixed parent.
Research the INDUSTRY Case first: SOTA, context, gap, attempts, question, benchmark basis, and supporting evidence.
Research a first-dozen target landscape and select FIRST, PEAK, FALLBACK, and OUTLIER.
Derive CANDIDATE Cases only where public evidence supports a useful prospect-specific STATE.
When proprietary analysis is authorized, research the Part 2 fields for the controlled Case.
Output: updated case background v#.3 or human-revision successor.

7. Control case background (B)
Input: background.txt with LEVEL=CASE, DOMAIN=D, and PROBLEM=P.
Check parent fidelity, industry SOTA, Case type, evidence status, target selection, candidate inference, benchmark basis, and any proprietary claims.
Return defects to R until controlled.
Output: controlled case background v#.4 or human-revision successor.

8. Compile case set (C)
Input: compile.txt with LEVEL=CASE, DOMAIN=D, and PROBLEM=P.
Compile controlled Case cards under 000_DOMAIN.txt and add them to the existing foreground under P.
Do not require Cases for other Problems.
When proprietary analysis is controlled, update the same Case card rather than creating a second Case.
Output: updated problem-and-case foreground v#.3 or human-revision successor.

9. Control case foreground (F)
Input: foreground.txt with LEVEL=CASE, DOMAIN=D, and PROBLEM=P.
Check Case fidelity, type, stage, anonymity, SOTA or STATE, gap, question, identifiers, and any proprietary Part 2 claims.
Return content-compilation defects to C. Return substantive evidence defects to R/B.
Output: content-controlled foreground v#.4 or human-revision successor.

10. Normalize case output (O)
Input: output.txt with LEVEL=CASE, DOMAIN=D, and PROBLEM=P.
Normalize the content-controlled Case cards under workflow/5_output.txt.
Do not change claims, IDs, type, stage, SOTA, STATE, proprietary findings, references, or tags.
Output: presentation-controlled foreground v#.4 or human-revision successor.

STOP -- Human inspection and explicit go-ahead required after each Case run and before proprietary analysis, another Case, or stabilization.


11. Stabilize
Input: controlled foreground (v#.4), controlled background (v#.4)
Persist controlled foreground as v(#+1).0.
Retain controlled research file in background as support for that stable foreground.

Version rule
Background and foreground are versioned independently.

Background
v#.1  problem research
v#.2  controlled problem research
v#.3  case research
v#.4  controlled case research

Foreground
v#.1  compiled problem set
v#.2  controlled problem set
v#.3  compiled problem and case set
v#.4  controlled problem and case set

v(#+1).0  stable

Odd stage .1, .3 = produced.
Even stage .2, .4 = independently controlled.
.0 = stable.

Human revision suffix
First digit after the point is workflow stage. Additional digits count human revision calls.
First clean run: v#.1, v#.2, v#.3, v#.4.
After first human revision call: v#.11, v#.21, v#.31, v#.41.
After second human revision call: v#.12, v#.22, v#.32, v#.42.
etc.
Version labels are workflow codes, not decimal numbers.

Operation rules
000_DOMAIN.txt is normative.
Research expands; compilation contracts; F controls content; O normalizes representation.
R and B work on background.
C compiles foreground content.
F controls foreground content and does not edit it.
O may change representation only.
Background is evidentiary and retained in full.
Foreground is canonical, terse, and version controlled.
Content defects return to C or R/B.
Output-format defects return to O.
O must stop rather than repair a content defect.
Do not descend from Problems to Cases before presentation-controlled problem foreground and human approval.
Run Case work only for selected Problems; do not force a Case for every Problem.
Review the Case taxonomy and workflow after each calibration Case and amend only when an observed defect earns a rule change.
Research establishes dependencies; compilation derives Problem sequence and numbering.
Industry Domain identity and code are inputs to the workflow. If research exposes an identity defect, flag it for ontology-level review; do not rename, recode, split, or merge the Industry Domain inside R → B → C → F → O.
The Problem Marketplace is the fallback for materially credible borderline or transferred Domain-ownership cases; ordinary exclusions and ordinary uncertainty stay in domain research.

Versioning
Use version control for all intermediate revisions.
Controllers do not edit the artifact they check. 
Control is conducted through the version-control review record.
Controllers issue findings and proposed corrections. 
The responsible Researcher or Compiler implements or rebuts them.
Control repeats through review and correction until PASS. 
Only then is the artifact promoted to the controlled stage version.
The version-control review history is the control record.
Do not persist separate QC documents or inline control appendices.
Do not create candidate, confirmed, QC, or duplicate release documents.
